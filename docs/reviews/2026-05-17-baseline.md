# ZiggyZag Review — May 17, 2026

A third-party walkthrough of the repo at `master` (commit `51e0a2b`). Scope: code quality and architecture, product gaps, process and velocity, docs and onboarding. The goal is to be useful, not flattering.

## TL;DR

ZiggyZag is in unusually good shape for its age. The repo is three days old, sits at roughly 16,600 lines of Zig across four binaries, has a coherent product story, and ships with brutally honest planning docs that already enumerate most of what is missing. The work that remains is real but legible — almost none of it is "we don't know what to do," and most of it is "this needs hours, not insight."

The single biggest structural risk is file size. Four files account for over 75% of the codebase, and the largest of them — `windows_app.zig` at 2,860 lines — has no test coverage. The single biggest process risk is that this is a solo project (108 total commits across all branches: 107 from one author, 1 from a bot) presented as a "team" effort, with no review gate and a CI matrix that does not include macOS.

The eight highest-leverage moves, in order, are at the bottom of this document.

## 1. Code Quality and Architecture

### What is good

The Zig itself reads well. Allocator threading is consistent (`self.allocator` on long-lived state, scoped arenas absent but `defer free` discipline is enforced). Error handling uses Zig's error union pattern throughout: roughly 960 `try` expressions in `shell/main.zig` against 69 `catch`, with no `@panic` calls anywhere in the codebase and only six `unreachable` markers total. There are no `std.debug.assert` calls — defensive asserts are a notable omission worth considering, but their absence is at least consistent.

Named limit constants live at the top of each file (`max_pipeline_capture_bytes = 8 * 1024 * 1024`, `max_completer_output_lines = 256`, etc.) which is exactly the right pattern. The agent's `Spec` enumeration and `Approval` enum in `apps/agentd/src/tools.zig` are well-designed: every tool declares its approval policy, effect, and context policy as data, not as scattered logic.

The recent security work is impressive for a three-day-old project. Commit `51e0a2b` ("Harden terminal, shell, agentd, config; fix file.read path traversal") and `5404d37` ("Harden agent file sandbox and fix provider-call deadlock") shipped a multi-layered sandbox: lexical path filter, final-component `lstat`, and a canonicalizing `realpath` workspace-containment check. The comment on `pathHasSymlinkComponent` even calls out the TOCTOU threat model explicitly. Tests cover sibling-prefix escapes (`/home/u/ws-evil/secret`), Windows ADS streams (`README.md:ads`), and `..` traversal.

Test coverage is uneven but not absent. `terminal.zig` has 82 test blocks for its VT parser — the right place to over-invest. `tools.zig` has 28. `config.zig` has 17. `shell/main.zig` has 19, which is light for 5,584 lines but better than nothing.

### What is concerning

**File size is the dominant problem.** Four files contain roughly 12,700 lines — about 77% of the codebase:

| File | LOC | Tests | Notes |
| --- | --- | --- | --- |
| `apps/shell/src/main.zig` | 5,584 | 19 | REPL, parser, builtins, history, jobs, completion, prompt — all in one file. |
| `apps/desktop/src/windows_app.zig` | 2,860 | **0** | Win32 host, paint, input, palette, settings overlay. |
| `apps/desktop/src/terminal.zig` | 2,744 | 82 | VT parser and grid. Best-tested big file. |
| `apps/agentd/src/tools.zig` | 1,520 | 28 | Tool implementations. |

`shell/main.zig` violates the docs' own stated principle ("the working shell lives in `apps/shell/src/main.zig`" — the architecture doc literally describes this as a feature). Splitting it along the natural seams that already exist in the file (`parser.zig`, `builtins.zig`, `history.zig`, `jobs.zig`, `completion.zig`, `prompt.zig`) would not require rewrites — these are already isolated logical modules sharing a `Shell` struct. Doing it now, while the codebase is young, is cheap. Doing it after another 5,000 lines is not.

`windows_app.zig` is more worrying because the entire Windows desktop host is one struct with one giant `wndProc` switch, and **it has zero test blocks**. The integration paths it owns — paint, input, paste, mouse wheel, palette, settings — are all reachable via the `App` struct's public methods, and at minimum the input-routing and palette-action paths could be unit-tested without a window. The inline Win32 binding constants and extern declarations occupy roughly the first 400 lines of the file (90 named constants, plus type aliases and struct definitions) before the first application enum appears. That entire block belongs in a `winapi.zig` module that both `windows_app.zig` and any future Windows-specific files can import.

**The shell tests are smoke-shaped, not unit-shaped.** `scripts/smoke.sh` is excellent as an end-to-end check, but it tests output strings (`grep -q "hello world"`), which means refactors that change phrasing break the build for cosmetic reasons. The 19 `test` blocks in `shell/main.zig` are not enough to characterize the parser, redirection, expansion, or job-control behavior precisely. A dedicated `parser_test.zig` with token-level assertions would catch regressions that the smoke test cannot.

**No fuzz, no sanitizers in CI.** Zig has `-fsanitize-c` and `-fsanitize-thread`, and the VT parser is exactly the sort of state machine that benefits from a fuzz target. The byte-split invariance test in `terminal.zig` is the right idea but is hand-written. A `zig build fuzz-parser` target running for 60 seconds in CI would catch a class of bugs that the current suite cannot.

**Cross-platform abstraction is leaky.** `apps/desktop/src/pty.zig` (47 lines) is a stub; the real PTY logic is in `windows_app.zig` (Windows) and `posix_pty.zig` (POSIX). The `Shared POSIX native desktop host` task (P0 item #7 in `NEXT_20_FEATURES.md`) acknowledges this — the boundary is the right thing to fix before adding a real macOS/Linux graphical host, because today's split makes it impossible to share UI code.

### Memory and resource hygiene

I did not find leaks in the patterns I sampled, but I also did not run the test suite. Two things to verify:

- The `BackgroundJob` struct holds an owned `std.process.Child`. Reaping logic on the Windows side should be checked under stress (the "deadlock tests" item under `NEXT_20_FEATURES.md` task #10 is open). The recent `5404d37` commit fixed a provider-call deadlock — there are likely more.
- The `windows_app.zig` reader thread now joins on shutdown (per task #6 in `NEXT_20_FEATURES.md`, marked shipped) but with no tests, regressions here will not be caught.

## 2. Product Gaps and Feature Completeness

The team's own `docs/ALPHA_TASKS.md` is the most accurate product gap document I could produce, so this section identifies things the planning docs **do not** call out, and ranks the things they do.

### Honestly stated, correctly prioritized

The roadmap is well-researched. The Ghostty/WezTerm reference pass in `NEXT_20_FEATURES.md` is the right bar to aim at, and the order — terminal correctness, then UX, then unique features — is correct. The P0 items in `ALPHA_TASKS.md` are exactly the right P0 items: VT conformance harness, Unicode graphemes, scroll margins, keyboard/mouse protocols, streaming pipelines, Windows raw input, POSIX PTY hardening, OSC 777 trust boundary, release smoke on real Linux/macOS hosts.

The decision to drop the Tauri/xterm.js spike (commit `66642bb`) is correct — embedding a JavaScript renderer in what is otherwise a Zig project would have created a permanent dependency cliff. Staying all-Zig is the right call given the team size.

### Gaps the docs underweight

**The macOS/Linux desktop story is more of a hole than the docs admit.** The launcher does run the shell in a terminal, and the POSIX PTY relay is real work, but "the macOS/Linux desktop is a terminal launcher" is functionally the same as "the macOS/Linux desktop does not exist as a product." Anyone trying ZiggyZag on a Mac will see a regular terminal running a Zig shell, which is interesting to engineers but not differentiated. If "main local terminal and shell" is the goal (`ALPHA_TASKS.md`), the gap between Windows and macOS is the single most important product gap, not a P2.

**There is no story for the agent panel without a local model.** The Quick Start troubleshooting section admits `provider_error` is expected when Ollama is not running. That is honest, but it means the agent panel — which is one of the three pillars of the workspace — is silent for every user who has not pre-installed Ollama and pulled a model. Either bundle a recommended model setup script, ship with a tiny local fallback (even rule-based), or remove the agent from the README's headline pitch until it is reachable out of the box.

**There is no user-facing changelog.** `dist/` has release manifests (`v0.1.0-alpha.1`, `v0.1.0-alpha.1-wave3-qa`, `v0.1.0-alpha.1-wave4-agent4`, `v0.1.0-alpha.2`) but no `CHANGELOG.md`. Friend testers who pick up `alpha.2` will not know what changed since `alpha.1` beyond reading commit messages. Add a `CHANGELOG.md` keyed by release tag, populated by hand for now.

**There is no telemetry, even opt-in.** Crash diagnostics and support bundles appear in `ALPHA_TASKS.md` as a P0 item (correctly), but the broader question — how does Pascal find out a friend tester's session crashed at midnight without them filing an issue — has no answer. A `~/.ziggyzag/crash/` directory that captures a stack and the last 200 lines of stderr on `@panic`/crash is cheap and high-value.

**There is no install path for non-developers.** The README assumes the user installs Zig, clones, builds. The release zips are real, but they need extraction and PATH manipulation. A one-line install command (PowerShell `iwr | iex` on Windows, `curl | sh` on POSIX) — even just one that downloads a release zip and unpacks it — would close the "I want to try this" loop.

**Theme parity between shell and desktop is not enforced.** The shell ships prompt themes (`classic`, `smart`, `compact`, `dev`, `dashboard`) and the desktop ships color themes (`ziggy`, `catppuccin-mocha`, …). The docs note "Sync prompt themes and terminal themes" as P1 work, but more concretely: today, picking `dracula` in the desktop does not coordinate prompt colors. A shared theme manifest format would let one selection drive both.

### Features that are over-promised

The README feature table lists `Pipelines` as `Alpha` and `Native pipelines` as a planned track. The note in the same table that "A true streaming pipe-chain engine remains future work" is correct. The risk is that the rest of the README's prose ("native simple pipelines, ..., complex syntax falls back to the system shell") undersells how often users will hit the fallback. Document the exact threshold ("pipelines with redirection on intermediate stages fall back to `/bin/sh -c` or `cmd /C`") so users can predict behavior.

The README also claims "Modern UX | Done." That is too strong. Cursor-aware autosuggestion UI is "needed on every platform" per the roadmap, syntax highlighting is "in smart prompt mode" only, and fuzzy Ctrl-R is described as not-yet-full-screen. Move this row to `Alpha` to match the rest of the table.

## 3. Process and Team Velocity

### The "team"

This is a solo project. 107 of 108 commits are from `PascalAI2024`; the remaining one is from `codecrafters-bot`. There is nothing wrong with solo projects, but two things follow:

1. **There is no PR review gate.** `master` is being committed to directly. The branch protection that the `.github/pull_request_template.md` implies does not appear to be enforced. For a hobby project this is fine; for anything Pascal wants others to trust enough to daily-drive, a "require PR + at least one approving review + CI green" rule is worth enabling even if Pascal is reviewing his own work — the act of opening a PR forces a second look at the diff.

2. **The "team" framing in this user's question is aspirational.** This review treats the work as one person's, because that is what the git history shows.

### Velocity

96 commits in 72 hours is a remarkable pace, and the commit messages are clean and topic-focused ("Harden terminal, shell, agentd, config", "Implement daily-driver safety wave", "Polish alpha release edge cases"). The "wave" structure visible in the log is healthy — features ship in coherent batches rather than dribble.

That said, sustained pace at this level is impossible. The risk is not burnout per se but staleness: an alpha that sits at the same readiness level for a month after the initial sprint because all the easy work was done in the sprint and the remaining items in `ALPHA_TASKS.md` are heavier. Two ideas:

- Pick three concrete items from `NEXT_20_FEATURES.md` and time-box them to one week each, starting with the VT conformance harness (task #1) because it unblocks confident parser work later.
- Defer the next release tag until at least one of {macOS native window, durable history backend, tabs} is in. Tagging frequently is good — but `alpha.2` to `alpha.3` should advance one of the headline gaps, not just be a patch roll-up.

### CI and release process

The release process is unusually thorough for a solo project. `scripts/build-release.ps1`, `scripts/qa-release-artifacts.ps1`, `scripts/daily-driver-qa.ps1`, `scripts/qa-tomorrow.ps1` — there is more release tooling here than many production teams have. The five-target cross-build is impressive. `release-artifacts.yml` workflow_dispatch is a sensible escape hatch.

The gaps:

- **No macOS in CI at all.** `ci.yml` runs on `ubuntu-latest` and `windows-latest`. Adding `macos-latest` would catch Darwin-specific PTY bugs immediately. GitHub-hosted macOS runners are slower and pricier than Linux/Windows, but for a workspace whose roadmap promises native macOS support, not testing on Darwin is a gap.
- **No release smoke on Linux or macOS.** The release artifact workflow runs only on Windows. The Linux and macOS zips are cross-built and never executed by CI. The docs acknowledge this ("Linux/macOS runtime smoke still needs real Linux/macOS hosts or CI runners"). Add `macos-latest` and `ubuntu-latest` jobs to `release-artifacts.yml` that extract the relevant zip and run `./ZiggyZag --version` (or equivalent smoke).
- **No `release.yml` triggered by tag push.** Today, releases are manual via `workflow_dispatch`. A `on: push: tags: ['v*']` workflow that runs the same package + QA path and attaches zips to a draft GitHub Release would close the loop.
- **No status badge for the release workflow.** The README has a CI badge; it should have one for `release-artifacts.yml` too, so friend testers can see whether the latest release built cleanly.

### Housekeeping

A few small things:

- **`.opencode/` (61 MB) and `.worktrees/` (404 MB) are not in `.gitignore`.** They are not currently tracked because everything inside happens to be `node_modules` or worktree internals, but `.gitignore` should make this explicit so they cannot accidentally land in a future commit. Add `/.opencode/` and `/.worktrees/` to `.gitignore`.
- **Two prunable worktrees on disk.** `git worktree list` shows `feature/ux-revamp` and `fix/docs-cleanup` as prunable. Run `git worktree prune` and remove the directories, or finish-and-merge the branches. 400 MB is not free.
- **The `.mavis/` and `.opencode/` directories suggest AI tools are in use.** That is fine, but consider committing a `.editorconfig` and a brief CONTRIBUTING note about which AI-assisted patterns are welcomed so collaborators do not have to guess.

## 4. Documentation and Onboarding

The documentation is the most pleasantly surprising thing in this repo.

### What is good

22 markdown files, an interlinked hub (`docs/README.md`), explicit ownership statements (`SCOPE.md`), separate planning surfaces (`ROADMAP.md`, `NEXT_20_FEATURES.md`, `ALPHA_TASKS.md`), an architecture diagram, contributor tour, a release checklist, a terminal parser guide, an agent protocol guide, a theme authoring guide, a daily-driver QA script, and a friend-test runbook. The Mermaid diagrams in `README.md` and `ARCHITECTURE.md` are accurate to the code.

`docs/ALPHA_TASKS.md` is particularly good — it splits work by priority, marks shipped items with concrete commit-evidence prose, and refuses to overclaim. The "Main Terminal Gate" section at the bottom of `NEXT_20_FEATURES.md` is the right kind of gate: a falsifiable list of conditions, not a vibe.

A new developer can build, run, and smoke-test the project in under 10 minutes following `QUICK_START.md`. That is rare.

### What is missing

- **No top-level `CHANGELOG.md`** (see Product Gaps).
- **No `SECURITY.md`.** The recent path-traversal fix shows security matters to this project. A two-paragraph `SECURITY.md` ("report to email X, expect a reply in N days, scope is …") would be cheap.
- **No glossary.** ZiggyZag uses several invented or borrowed names (AgentD, OSC 777, "wave", "alpha line") in passing. A `docs/GLOSSARY.md` would help readers who have not read every file.
- **`apps/shell/README.md` exists but is short** — and it does not describe the file structure inside `apps/shell/src/`. Today that file structure is "one file," but after the recommended split it will need a guide.
- **The docs hub does not link to itself from `CONTRIBUTING.md`.** A new contributor lands on `CONTRIBUTING.md`, which mentions the test commands but not the existence of `docs/`. One link in the "Setup" section closes that gap.
- **Slightly redundant docs.** `ROADMAP.md` and `FEATURES.md` overlap with `NEXT_20_FEATURES.md` and `ALPHA_TASKS.md`. The four documents each have a clear identity in Pascal's head, but a first-time reader has to read all four to understand "what is the plan." A one-paragraph header on each, in the form "Use this doc when X; for Y use Z," would resolve this without merging anything.

### Onboarding test (hypothetical new contributor)

Path: clone → `zig build` → `zig build test` → read `docs/README.md` → pick something from `CONTRIBUTING.md`'s "Good First Contributions" list (e.g., "Improve parser diagnostics").

This works. The "Good First Contributions" list is genuinely well-curated. The friction points: the new contributor has to discover that all the parser code is in `apps/shell/src/main.zig`, which is 5,584 lines. They will Ctrl-F. They will succeed, because the code is readable, but the experience would be much better with a split module structure.

## 5. Eight Highest-Leverage Moves

Ordered by (impact ÷ effort). The first three are days of work; the rest are hours.

1. **Split `apps/shell/src/main.zig`** into `parser.zig`, `builtins.zig`, `history.zig`, `jobs.zig`, `completion.zig`, `prompt.zig`, and a thin `main.zig` that orchestrates them. Each file gets its own `test` blocks. Do this before the file passes 6,000 lines.
2. **Add `macos-latest` and a Linux release-smoke job to CI.** Two lines in `ci.yml`, two jobs in `release-artifacts.yml`. The macOS-shaped bugs that exist today will surface within a week.
3. **Pick one of {durable SQLite history, tabs, native macOS window} and tag `alpha.3` only after it ships.** Headline gaps need headline fixes; another patch release will not move the daily-driver bar.
4. **Add a `CHANGELOG.md`** keyed by release tag, populated for `alpha.1` and `alpha.2` from the commit log.
5. **Add `.opencode/`, `.worktrees/`, and `dist/` to `.gitignore`** explicitly (some are already there; verify the patterns cover the worktree directories), and `git worktree prune`. Reclaim ~400 MB.
6. **Add a `winapi.zig` module** with the Win32 constants and function externs currently inline at the top of `windows_app.zig`. Pure mechanical refactor; ~400 lines moved, no behavior change.
7. **Write ten unit tests for `windows_app.zig`'s palette-action routing and keybinding dispatch** — the parts reachable without a window. Zero coverage today is the largest single risk in the codebase.
8. **Add a `SECURITY.md` and a `release.yml` that fires on `v*` tags.** Both are 30-minute jobs. The first signals that security is a concern; the second removes a manual step from every release.
